# The Pale Cap: save-system investigation

Investigated October 11, 2026. This records historical engine analysis and proposed integration, not the current save implementation.

## Decision

**Use GB Studio's existing snapshot save/load, keep gameplay persistence in named script variables, and restore an idle dwarf through a dedicated restore path.** Do not serialize the native FIFO for this slice. Add a small native integrity/selection wrapper around two engine slots if the requested checksum, interrupted-write recovery and four-way Continue status are required. Those guarantees are absent from ordinary events. A new item serializer or replacement persistence framework is unnecessary at this scale.

Saving retains the current expedition. Only successful return changes its secured status; deposit moves ownership. Neither Save nor Continue should award extraction, refresh a shelf, abandon inventory, or recreate discoveries. Six bag slots, twelve stash slots and retreat losses remain provisional gameplay settings ([slice](../../the-pale-cap/EXPEDITION-SLICE.md), [TODO](../../the-pale-cap/TODO.md)).

## What the engine actually persists

The authoritative list is [load_save.c lines 32–54](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/appData/engine/gbvm/src/core/load_save.c#L32):

1. Entire `script_memory`: global variables **and VM stacks**, 3,584 bytes here. `VM_HEAP_SIZE=768`, 16 contexts × 64 stack words, each word 16 bits ([vm.h](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/appData/engine/gbvm/include/vm.h#L71)). Names in the editor are not physical indices: latest generated aliases and compiler allocation govern addresses. Resolve through `getVariableAlias`, as the controls event already does ([event](../../the-pale-cap/plugins/colony-controls/events/eventColonyControls.js)). Do not index `script_memory[42]` expecting editor variable ID `42`.
2. All `CTXS` (304 bytes), scheduler pointers and VM lock state. A save resumes script execution; it is not merely a bag of variables loaded into a fresh scene.
3. Input bindings/slots, timer events/values, music track pointer/bank and music events. Music is restarted, not resumed sample-exactly ([load_save.c](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/appData/engine/gbvm/src/core/load_save.c#L135)).
4. Current scene far pointer, scene stack pointer and stack; complete actors array (1,176 bytes), active/inactive heads, player movement and collision actor. This includes both cursor PLAYER and Bram's actor state, not just player position.
5. RNG seed.

Not in that list: arbitrary plugin C statics, `game_time`, transient screen/window contents, full music-driver state, palettes/tile mutations, projectiles, every engine field, or historical actors for every visited scene. `load_scene(..., FALSE)` reloads background/palettes/triggers from ROM, resets projectiles and makes active actor animation idle; it **does not run scene Init** ([core.c](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/appData/engine/gbvm/src/core/core.c#L139), [data_manager.c](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/appData/engine/gbvm/src/core/data_manager.c#L192), especially lines 261–343). Restore dynamic visuals from semantic variables. Ordinary scene changes also rebuild scene actors, so persistent world changes must live outside those actors.

The native `orders[16]`, `count`, `active`, `closed` and cursor-repeat fields are C statics ([ff_controls.c](../../the-pale-cap/plugins/colony-controls/engine/src/ff_controls.c)). They are **not saved**. Cold boot zeros them; loading within a running session can retain unrelated current values. `operation: 0` clears count/active/closed/input state and variable 42 via OUTPUT(3), but does not clear every script-side worker field (lines 29–33). `last_cursor_frame` is not reset; `last_direction=0` makes the next direction an initial press. A more explicit reset can set it too, but it is not a persisted gameplay requirement.

## Size, layout and compatibility constraints

[load_save.h](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/appData/engine/gbvm/include/load_save.h#L6) limits normal saves to **three SRAM banks** of 8,192 bytes, although the ROM advertises four. [Slot placement](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/appData/engine/gbvm/src/core/load_save.c#L77) packs whole blobs into banks without crossing a bank. At 5,325 bytes, slots 0, 1 and 2 each occupy `A000–B4CC` in banks 0, 1 and 2 respectively. There are 2,867 unused bytes at each bank's tail. Bank 3 is not used by this engine save list; do not silently claim it for unrelated systems.

Blob format: 4-byte little-endian signature, 2-byte total size, then 23 blocks, each `u16 size, u8 ID, payload`. Thus `6 + 23×3 + 5250 = 5325`. The first variable starts at byte offset 9. Slot addresses depend on blob size; they are not universally bank N. Recheck after engine/plugin changes. `data_slot_address` does not reject an oversized blob for slot zero: add a build/runtime bound assertion, not an assumption that the engine will protect it.

The global heap is 768 words; growing used aliases within it does not enlarge the fixed 3,584-byte script-memory save block. Latest build uses 41, leaving 727 nominal global words before new locals/shared allocations and compiler decisions. Validate the resulting build's globals and WRAM budget. Compiler global-count check: [validateEjectedBuild.ts](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/src/lib/compiler/validate/validateEjectedBuild.ts#L17). Do not enlarge VM heap just because SRAM remains.

The signature is a 32-bit hash of `JSON.stringify(projectData)`, generated by [compileData.ts](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/src/lib/compiler/compileData.ts#L2088) and [generateGBVMData.ts](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/src/lib/compiler/generateGBVMData.ts#L1392). It is **neither a save checksum nor a stable game schema version**. Project edits can invalidate a save; external engine/plugin/asset edits may change execution layout without a corresponding safe compatibility guarantee. Saved ROM addresses and WRAM pointers mean snapshots should be accepted only for the exact approved build/ABI. Add an explicit build-compatibility identifier to validation metadata. Never force a constant engine signature to make old snapshots load.

Cross-release migration is deliberately deferred: a stable variable schema does not make saved VM contexts portable. Reject incompatible snapshots safely. If migration becomes a requirement, decode a separately versioned semantic payload into a new runtime; do not load old contexts. That is additional work, not needed to prove the same-build first loop.

## Supported events and APIs

[Official save-event documentation](https://www.gbstudio.dev/docs/scripting/script-glossary/save-data/) exposes three slots, Game Data Save/Load/Remove, an existence condition and reading a saved variable. The installed implementations are the behavioral authority:

- `EVENT_SAVE_DATA`, `args.saveSlot: 0|1|2`, `children.true` = On Save and `children.load` = On Load ([eventDataSave.js](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/src/lib/events/eventDataSave.js#L3)). Compiler helper `dataSave(slot, onSave, onLoad)` raises `EXCEPTION_SAVE`, then uses `VM_POLL_LOADED` to choose a branch ([scriptBuilder.ts](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/src/lib/compiler/scriptBuilder/scriptBuilder.ts#L3508)). **Continue lands in the saved event's On Load branch**, not scene Init or the title's next statement.
- `EVENT_LOAD_DATA` / `dataLoad(slot)` raises `EXCEPTION_LOAD` ([scriptBuilder.ts](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/src/lib/compiler/scriptBuilder/scriptBuilder.ts#L3501)). Only invoke after full preflight validation.
- `EVENT_IF_SAVED_DATA` / `ifDataSaved` calls `VM_SAVE_PEEK` with count zero. It tests the signature only ([scriptBuilder.ts](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/src/lib/compiler/scriptBuilder/scriptBuilder.ts#L4048)). It is not corruption detection.
- `EVENT_PEEK_DATA` / `dataPeek(slot, source, destination)` reads a saved global through its compiled alias; failure writes zero ([scriptBuilder.ts](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/src/lib/compiler/scriptBuilder/scriptBuilder.ts#L3565)). Suitable for previews after integrity validation, not validating a file by itself.
- `EVENT_CLEAR_DATA` / `dataClear(slot)` clears the signature only. A wrapper with metadata must invalidate that metadata too.
- Native APIs: `data_save(slot)` returns **void**; `data_load(slot)` and `data_peek(slot, idx, count, dest)` return boolean; `data_clear(slot)` returns void ([header](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/appData/engine/gbvm/include/load_save.h#L14)). Prefer the events for save/load scheduling and On Load behavior. Do not call `data_load` from an arbitrary native event and then keep using the overwritten VM context.

[GBVM primary reference](https://www.gbstudio.dev/docs/scripting/gbvm/gbvm-operations/) documents the exception, poll and peek operations. Installed engine save processing is synchronous at the VM exception boundary ([core.c](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/appData/engine/gbvm/src/core/core.c#L135)). This stops concurrent script progress during the copy; it does **not** make power-loss writes atomic.

## Required semantic state (recommendation)

Use bounded records in named global variables. Define capacity constants for the current experiment; schema-version changes accompany layout changes, without making test capacities permanent rules.

- **Item registry:** nonzero stable instance ID; definition ID and definition revision; resolved intrinsic values/imprint/provenance actually implemented; explicit mutable state; exactly one location enum plus optional position within that location. With one authored unique fork, an assigned stable ID is sufficient. Introduce an allocator/next-ID only when repeatable instances exist; never reuse live IDs or silently wrap. Future cross-cartridge trading needs a namespace, separately scoped.
- **Bag/stash:** derive membership from the registry location. If UI needs ordered slot arrays, store references and validate unique membership, never duplicate item records. Equipment is a nullable instance-ID reference into the bag, **not another owner or slot-freeing move**. Deposit of an equipped item must unequip in the same commit. Reject dangling/duplicate references rather than manufacture replacement items.
- **Intrinsic properties:** persist resolved values once when assigned. For this fixed authored fork, definition+revision may identify immutable ROM data only while that revision/build is enforced. Any assigned per-instance property must be a saved field. Do not recompute intrinsic values from present view, new generator code or a seed alone. Effective view/equipment modifiers remain derived. This follows [DESIGN](../../the-pale-cap/DESIGN.md) and [stable identity](../../the-pale-cap/DESIGN.md).
- **World collection:** stable object IDs independent of actor index, sprite or view; bitset/flags per logical map and, where applicable, expedition generation. One underlying object has one collected flag across views. Store regrowth separately from unique-object collection so mushroom replenishment cannot recreate the fork.
- **Economy/home:** carried and stored resource counts with bounds; secured/carried distinction separate from physical container; improvements purchased and their levels; shelf reserve, refresh eligibility and last credited expedition/gathering progress if the provisional shelf rule is implemented. Purchase debit and improvement flag commit together.
- **Knowledge/dwarf:** learned concepts, persistent encounter progress/connections, selected spell, exposure and any implemented health/status; Bram position/direction and cursor position. Capture semantic coordinates explicitly even though actors are snapshotted, because the recommended restore path recreates the scene.
- **Expedition:** home/away mode, stable logical map ID, expedition ID if needed, entrance/return target, collected/world-state bits, gathered-this-trip counters and any retreat/extraction bookkeeping. Save outside the transition transaction, never midway between debiting/depositing/changing scenes.
- **Paid timed effects:** remaining gameplay ticks plus snapshotted endpoint mask for a paid pulse. Preserve these through reload without paying again; derive markers from endpoints minus collected IDs. Ambient animation phase can restart. If an active paid effect cannot be represented, defer Save until it completes—do not silently consume its benefit on Continue. No offline catch-up.

Keep temporary menu choices, worker target/type/step/result, pending counts and admission barriers transient. Exclude reservation mechanics initially: validate and pay at execution, not enqueue. If the main implementation introduces reservations, a save boundary must cancel/refund each reservation exactly once before capture.

## Concrete integration sequence

1. **Centralize commits first.** Collection checks capacity at completion and atomically sets object-collected + registry ownership. Transfer changes location and equipment reference together. Use validates equipment/connectivity/resources and commits debit + effect together. Purchase commits debit + improvement. Run each short transaction under `VM_LOCK`/`VM_UNLOCK` (event helper `lock()/unlock()`), with no waiting/dialogue between debit and result. The VM normally time-slices even non-waiting scripts after its instruction quantum ([scheduler](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/appData/engine/gbvm/src/core/vm.c#L761)); short source code alone is not a transaction.
2. **Expose a save request and boundary.** Save in the Start overlay sets `save_requested`, closes the overlay and lets the worker reach a boundary. Do not hold the menu's VM lock while waiting for the worker: it cannot run. Stop accepting new orders, allow a currently working harvest/pulse/talk to finish, stop before starting another order; for traveling orders stop at a completed tile and discard the unfinished order. Coordinate through explicit worker phase/boundary variables. Never decrement a pending counter again after clearing it.
3. **Canonicalize under lock.** Park the worker at the top of its loop with no outstanding movement/wait/cost. Clear pending reservations/designations; harvest state 1/2 becomes available only when no reward was committed, state 3 stays harvested. Call `EVENT_COLONY_CONTROLS {operation:0}`. Clear variable IDs 29, 31 (if used), 38–42 and relevant target scratch; recapture worker/cursor coordinates rather than zeroing persistent positions. Clear the return/talk admission barrier. The existing worker marks harvest state 2 before movement and later waits 90 frames before reward ([worker](../../the-pale-cap/project/scenes/start/actors/bram_cinder.gbsres), [reward](../../the-pale-cap/project/scenes/start/actors/bram_cinder.gbsres)); resetting C alone leaves those scripts able to award later.
4. **Capture and save.** Validate registry ownership/reference invariants, schema and logical scene; store the semantic positions and effect state. Choose the inactive engine slot via the integrity helper below. Invoke one of two literal-slot `EVENT_SAVE_DATA` branches while still locked; both must have identical restore behavior. On Save verifies persistence through the wrapper before showing success; unlock and resume the canonical idle worker afterward. Clearing orders on the live Save path too is the simplest consistent behavior; tell the player that orders were cleared.
5. **Continue/On Load.** Preflight at the title, invoke the selected `EVENT_LOAD_DATA`. In the saved **On Load** branch, before yielding/unlocking, reset the native queue again (warm loads matter), set `restore_mode`, and issue ordinary Change Scene to the saved logical location. This intentionally discards restored execution contexts through `EXCEPTION_CHANGE_SCENE` ([core.c](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/appData/engine/gbvm/src/core/core.c#L118)). A restore-aware Init recreates Bram/cursor, object visibility, dynamic network/view visuals, effects, handlers and idle worker from semantic variables, then clears `restore_mode`. It must skip New Game initialization and the boot menu. This removes any dormant saved reward/talk continuation instead of hoping queue reset neutralizes it. Guard actor-update scripts until restoration finishes. Audit menu/lock balance and fade behavior; the Save helper injects On Load fade handling.
6. **Split fresh start from scene entry.** Current [scene Init](../../the-pale-cap/project/scenes/start/scene.gbsres) runs Colony Boot then controls initialize, and [boot event](../../the-pale-cap/plugins/colony-controls/events/eventColonyBoot.js) only offers New Game/Controls. Put title selection and New Game seeding behind explicit fresh-start logic; ordinary home entry and restore must never reset exposure/inventory/knowledge or show the title again.
7. **Extraction/deposit remain gameplay transactions.** Arrival + confirmation commits home/secured state and coordinates, clears scene-bound orders, then transitions. Save only after this settles or before it starts. Full stash leaves excess carried. Autosave after extraction can use the same path, but cannot substitute for an expedition Save option. Continue always returns to the last committed save's home/expedition state; unrequested power-off cannot save changes since that checkpoint. A deliberate Save-and-Quit must wait for verified completion.

## Integrity and recovery: absent engine guarantees, minimal addition

**Verified gaps:** writer writes the signature first and overwrites in place; there is no checksum, commit marker, generation or previous-record copy ([writer](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/appData/engine/gbvm/src/core/load_save.c#L90)). Loader checks signature and each block's size/ID, but copies blocks as it goes: a late failure can leave variables/contexts partially replaced. It skips rather than verifies stored total length ([loader](https://github.com/chrismaltby/gb-studio/blob/v4.3.2/appData/engine/gbvm/src/core/load_save.c#L118)). Peek checks only the signature and does no bounds/structure verification (line 155). `On Save` runs even though `data_save` has no success result. Neither that branch nor `If Game Data Saved` proves successful physical persistence.

**Recommended small extension, not existing API:** keep engine slots 0 and 1 as alternating whole snapshots. Add native events such as `Pale Save Scan`, `Pale Save Begin`, `Pale Save Finish`. They validate/read SRAM but delegate snapshot serialization and restoration to the existing events. No external plugin dependency is needed.

For this build, reserve a fixed **32-byte trailer at BFE0–BFFF in each of banks 0 and 1**. Define byte order and offsets in one header: magic (4), wrapper version (2), gameplay schema (2), explicit build compatibility ID (4), sequence (4), blob length (2), reserved (2), CRC32 (4), reserved (7), commit byte (1). CRC covers blob plus trailer metadata excluding CRC and commit. Zero reserved bytes. Use unsigned wrap-aware sequence comparison. This is a proposed layout, not bytes the existing engine writes.

Require `4096 < save_blob_size <= 8160` and that actual slot addresses are bank 0/1:A000; fail build/startup otherwise. The lower bound prevents packed slots sharing a bank and colliding with this simple trailer scheme. Check the ROM RAM/mapper settings as well. Leave slot 2 unused; do not expose all three as player slots while reserving two for one save history.

Save protocol: preserve the newest valid slot; invalidate and read back the target's commit byte; write new metadata with commit invalid; call the engine Save event; in On Save compute/read back CRC and validate all block sizes/IDs/length, signature, schema, build ID and semantic invariants; write commit last; rescan successfully before reporting Saved. For write verification, retain a pre-write expected checksum of the canonical gameplay fields and compare the saved variable block to it; otherwise a checksum computed only from read-back could certify an already bad write. The engine context snapshot itself must be checksummed after its save exception, not before its PC advances. Abort on any verification failure and leave the previous slot valid. Keep gameplay locked throughout.

Load protocol: validate the **entire candidate** without copying into engine RAM; check bounded length before CRC, expected block structure and signature, exact build compatibility, gameplay schema and ownership invariants. Only then call Game Data Load. Select newest valid compatible sequence, fall back to previous if latest is incomplete/corrupt, and report recovery. Do not automatically overwrite the incompatible/corrupt record merely by opening the title. This preflight prevents the engine's partial-load failure path.

This provides ordered commit/recovery under ordinary independent SRAM writes; it is not proof of hardware atomicity. CRC detects accidental corruption probabilistically, not malicious tampering. Readback cannot prove long-term retention. Actual cart save hardware and any flash-backed flush behavior need testing. If a cart rewrites multiple banks in one erase operation, two logical records alone may not survive a physical interruption.

## Continue states

- **No save:** no recognized committed record; ordinary erased/uninitialized storage. Show New Game. A recognizable incomplete first save should instead say saving was interrupted. With no surviving identification bytes, no implementation can perfectly distinguish arbitrary garbage from a never-used cart.
- **Valid:** complete metadata, full integrity/structure checks, compatible build/schema and valid semantic references. Enable Continue and restore that record. A valid previous record takes precedence over a corrupt latest, with a recovery notice.
- **Incompatible:** recognizable, integrity-valid Pale Cap record with unsupported wrapper/schema/build identity. Explain that this build cannot continue it; preserve bytes. A simple signature mismatch alone cannot prove incompatibility rather than corruption.
- **Corrupt/interrupted:** recognized record fails commit, bounds, CRC, structure or semantic checks; use previous compatible record if available, otherwise disable Continue with an explicit message. Do not quietly start a new expedition.

Stock `If Game Data Saved` collapses these distinctions. A saved schema variable alone cannot fix that: old signatures block peeking and variable indices can move. Fixed-location metadata is why the small wrapper is justified. Legacy engine-only saves have no trailer; treat them as unsupported/unvalidated, not trusted snapshots. There are no implemented Pale Cap saves in the inspected source to migrate.

## What has and has not been tested

**Verified here:** installed version probes; engine/compiler/control source inspection; actual ROM headers, compiled save-point layout and aliases; primary docs. Read-only analysis succeeded. No new ROM build or gameplay/emulator save/load test was run. Existing PLAYTEST evidence covers gameplay, not persistent saves.

**Emulator-verifiable next:** exact-ROM cold restart from a battery `.sav` (not a full emulator state); safe-boundary gating, On Load path and no surviving worker continuations; ownership/intrinsics and scene restoration; artificially truncated/torn/corrupted SRAM records and previous-slot selection; incompatible schema/build refusal; no-save UI. Use isolated ROM/save paths under an authorized probe folder. Emulator snapshots preserve extra machine RAM and would conceal this native FIFO problem. Browser persistence is a separate test: same export identity/storage and actual reload must be checked; switching ROM identities can intentionally separate saves.

**Requires actual cart testing:** compatible mapper/RAM implementation, real persistence across power cycle, retention, save duration and user feedback, interrupted-write behavior and independence of records under its storage firmware. A ROM header requesting battery RAM does not establish the installed cartridge's storage technology. No hardware discovery, streaming or flashing was performed. Do not turn on GB Studio batteryless mode to compensate without identifying the cart and its supported flashing/save mechanism.
